# Add polix rules fmt and reject repeated rule ids in the loader of the rules

- Status: built
- Risk: high: it changes the command line (`polix rules check` stops on a new case, a new command writes files) and the
  delivery of the repository (`just check`, `polix.yaml`).
- Reference: none.
- Created: 2026-11-11.
- Size: 5 tasks, about 1150 changed lines.

## Overview

Today `polix config fmt` formats only `polix.yaml`: the files of rules in `ai/rules/` are never formatted, and
nothing keeps their layout uniform.
This change adds `polix rules fmt`, which formats every rules file in place the way `polix config fmt` formats
`polix.yaml`, and with `--check` only tells whether they are formatted.
It either formats every file or none: when one file cannot be formatted, it writes nothing.
It leaves one blank line between two rules, so each rule reads as its own block.

It also makes sure that no two rules share an id.
`polix config check` already reports a repeated id among the active rules, but `polix rules check` does not.
The check moves into the shared reading of the rules, so `polix rules check`, `polix rules fmt`, `polix config check`
and `polix doctor` all see it.
An id of a retired rule now counts as taken too.

Finally the repository uses the new command itself: `just check` runs it with `--check`, the hooks format a rules file
right after it is edited, and the rules of this repository are formatted once.

## Context

`polix config fmt` is the use case `internal/app/workflow/format`: it reads `polix.yaml`, formats it with
`yamlfmt.Format` and an order of keys, and writes it or, with `--check`, exits with 1 when it would change.
The rules are read by the loader `internal/app/rule/load`, which skips `retired.yaml` and reports invalid rules in
`rule.Loaded.Problems` and `rule.Loaded.Strict`; repeated ids are found only by `setup.Inspection.RuleProblems` through
`rule.Rules.Repeated`, so `polix config check` and `polix doctor` report them but `polix rules check` does not.
The domain `internal/app/rule` has only the use cases `check` and `load`, and no command formats the rules files.

  the convention of the commands of the repository.

  `polix rules check` stops, `polix rules fmt` fails, and `polix config check` and `polix doctor` report it: interview.

- `polix rules fmt` with a repeated id, with or without `--check`, reports it to stderr, writes nothing and exits

- Besides `just check`, the `polix.yaml` of this repository runs `polix rules fmt` in `format_on_edit` for

- The long line that the format leaves in the `scope` of GOARCH-22 of `ai/rules/architecture.yaml`, a flow sequence
  written on one line, is accepted as the format leaves it: interview.
- Exactly one blank line before each rule but the first, in every rules file, `retired.yaml` included; with comments
  above a rule the blank line goes above the comments; inside a rule the blank lines stay as today: interview.
- The blank line between the rules is an option of `internal/platform/yamlfmt`, which tells which sequences separate
  their items; `polix config fmt` passes none and does not change: interview.

## Approach

**Repeated ids in the loader.**
`rule.Rules.Repeated` takes the retired rules: their ids are taken first, with their file, so an active rule with a
retired id is reported as `<file> <id>: id repeated, also in <dir>/retired.yaml`, and repeats among the retired rules
are never reported.
The port of `internal/app/rule/load` gains `ReadRetired`, which returns the rules of `retired.yaml` with their file,
and nil when the file is missing, cannot be read or is not YAML; it never returns an error.
`Decide` of the loader takes the retired rules too, and adds to `rule.Loaded` the problems of the repeated ids:
in `Problems`, after those of the invalid rules, and in a new field `Repeated` that holds only them.
`Strict` stops at the first invalid rule, else at the first repeated id (an error with the text of its problem), else
at `err`.
With `err`, `Repeated` is empty like `Rules` and `Problems`; `Loaded.Valid` and `Loaded.Fail` cover the new field.
`setup.Inspection.RuleProblems` no longer calls `Repeated`, since `Loaded.Problems` holds the repeats.
`polix rules check` stops on `Strict` with no change to its code; the hooks read only `Rules` and `Err`, unchanged.

**Blank lines between the items of a sequence in yamlfmt.**
`yamlfmt.Format` takes a second function besides `Order`, a new exported type `Spaced`, that receives the path of a
block sequence (as `Order` does for a mapping) and tells whether its items are separated by one blank line.
For such a sequence the printer writes one blank line before each item but the first, above the comments of that
item, never two in a row, and never a blank line before the first item; the comments and blank lines read from the
source stay as they are, and the self check of `Format` (same data, same comments) holds.
`polix config fmt` (`formatData` of `internal/app/workflow/format/logic_order.go`) passes nil, which separates no
sequence, so its output does not change.

**The use case FormatRule.**
`internal/app/rule/format` follows the shape of `internal/app/workflow/format`, for a folder instead of one file.
`Request` holds `Dir` and `Check`, and the running version, to load the workflow.
The port has `LoadWorkflow`, which returns the workflow through the loader of `polix.yaml` and an error only when it
cannot be read, cannot be parsed or requires a newer polix (as `LoadWorkflow` of `internal/app/rule/check`).
It has `ReadRuleFiles`, the data of every `*.yaml` of the folder by name and whether the folder exists.
It has `WriteRuleFile`, which writes one file of the folder through `internal/platform/file`.
Task 4 adds `RepeatedIDs`, the `Loaded.Repeated` of the loader of the rules.
The shell loads the workflow, validates `rules.path` with a new method of the domain `workflow.Rules`, `ValidPath`,
reads the files, calls `Decide` once and writes each file of the output.
`Decide` takes the folder, the files, the repeated ids and `Check`, and returns `Output`.
`Output` holds the folder, whether there is nothing to format, the problems (each `<dir>/<name>: <problem>`, then the
repeated ids as the loader words them), the files that change (`<dir>/<name>`, sorted), the command that fixes them
(`polix rules fmt`) and the data to write by name.
The data to write is nil with any problem or with `Check`.
The order of the keys and the sequence to space, `rules`, live in `logic_order.go` of the use case, the only one that
needs them (GOARCH-10).
`Response` holds the folder, whether it was empty, the problems, the changed files, the written files and the fix.
The command prints it and sets the exit code.

**Delivery.**
`cmd/polix` adds the command under `rules`.
`just check` runs `polix rules fmt --check` after `polix config fmt --check`, and `polix.yaml` formats a rules file
after each edit.

### Discarded alternatives

- Repeated ids checked only in `polix rules check` and `polix rules fmt`: the user chose the loader, one place and one
  message for every command.
- A file argument to `polix config fmt` for the rules files: the order of the keys of a workflow is not that of a rule,
  and the user picked `polix rules fmt`.
- The ids found by decoding the files in the logic of `FormatRule`: the logic knows no format (GOARCH-41), and the
  loader already decodes them.
- Writing the files that can be formatted when another cannot: the user chose all or nothing.
- Inserting the blank lines between the rules in the text that `yamlfmt.Format` returns, in the logic of
  `FormatRule`: fragile with comments and block scalars; the user chose the option of yamlfmt.

## Acceptance criteria

- AC1: `polix rules fmt` formats in place every `*.yaml` of the folder of rules, `retired.yaml` included, with the
  layout of `polix config fmt` (two spaces of indentation, flow collections on one line, comments and blank lines kept).
  `rules` goes first at the top, and the keys of each rule go in the order `id`, `description`, `scope`,
  `deterministic`, `check`, `reason`, then the unknown keys in their order in the source; the rules never move.
  It prints `ok: formatted <file>` to stdout for each written file, with `<file>` as `<dir>/<name>`, and exits with 0.
- AC2: when no file changes, `polix rules fmt` writes nothing, prints `ok: the rules are formatted` and exits with 0.
- AC3: `polix rules fmt --check` never writes; for each file that would change it prints
  `<file> is not formatted: run polix rules fmt` to stderr and exits with 1; when none would change it prints
  `ok: the rules are formatted` and exits with 0.
- AC4: when the folder of rules does not exist or has no `*.yaml` file, `polix rules fmt` prints
  `ok: no rules to format in <dir>` and exits with 0, with or without `--check`.
- AC5: when any file cannot be formatted (not YAML, an anchor, an alias), `polix rules fmt` prints
  `<dir>/<name>: <problem>` to stderr for each such file, writes no file at all, and exits with 1.
- AC6: the folder is `rules.path` of `polix.yaml`, `ai/rules` without `polix.yaml`.
  A `polix.yaml` that cannot be read, cannot be parsed or requires a newer polix fails the command with its error,
  exit 1, nothing written.
  Any other problem of `polix.yaml`, such as an invalid runner of `rules.run`, does not stop it.
- AC7: a `rules.path` that is absolute, the root, outside the root or a glob fails `polix rules fmt` with
  `rules.path "<path>" <problem>`, in the words of `polix config check`, exit 1, nothing read nor written.
- AC8: the loader of the rules reports, for each active rule whose id an earlier active rule or a rule of
  `retired.yaml` already has, `<file> <id>: id repeated, also in <other file>`.
  `polix config check` and `polix doctor` report each such problem once.
  Repeats among the retired rules are not reported, and a `retired.yaml` that is missing, cannot be read or is not
  YAML changes nothing.
- AC9: `polix rules check` with a repeated id fails before running any check, exit 1, with the text of that problem;
  an invalid rule of an earlier file still wins, as today.
- AC10: `polix rules fmt` with a repeated id, with or without `--check`, prints
  `<file> <id>: id repeated, also in <other file>` to stderr, writes no file, and exits with 1.
- AC11: `polix rules fmt` takes `--dir`, any folder of the repository, defaulting to the current one, and no
  argument; outside a git repository it fails with the error of the repository.
- AC12: `just check` runs `polix rules fmt --check` and passes on this repository, the files of `ai/rules/` are
  formatted, and `polix.yaml` runs `polix rules fmt` in `format_on_edit` after an edit of `ai/rules/*.yaml`.
- AC13: `polix rules fmt` leaves exactly one blank line between two consecutive rules of every rules file, above the
  comments of the later rule when it has them, and none between `rules:` and the first rule; with `--check`, a file
  whose rules are not separated so is not formatted.
  `polix config fmt` adds no blank line it did not keep before.

## Out of scope

- Adding `polix rules fmt --check` to the commands an invalid workflow still allows in the hooks: the user left it out.
- File arguments to `polix rules fmt`: the user chose the folder of `rules.path` only.
- Reporting repeats among the retired rules, or a broken `retired.yaml`: the loader ignores that file as today.
- Any change to `polix config fmt`.
