# Run the githooks section of polix.yaml from git itself on pre-commit and commit-msg

- Status: built
- Risk: high: it adds a section to the format of polix.yaml, a new command that git runs on every commit, and writes
  the git configuration of the repository on install, also from every session start of a polix.yaml with githooks.
- Reference: none.
- Created: 2026-11-11.
- Size: 8 tasks, about 2500 changed lines.

## Overview

Today polix only governs the commits of the AI, and only when it recognises a `git commit` in a command line.
Commits made by people, from an IDE, or by the AI through forms the heuristic does not see, go through unchecked.
This change lets git itself call polix on every commit, whoever makes it.

A new section of polix.yaml, `githooks`, holds the gates git runs, apart from the events of the AI in `on`.
It has two events: `pre_commit`, before the commit is made, and `commit_msg`, once its message is written.
Their entries have the same shape as those of `on`, but a small vocabulary: they only `block` or `run` a command, and
their conditions are the branch, the files staged for the commit and, in `commit_msg`, the first line of the message.
So a repository can demand a message format by branch or by the files a commit holds, and run a command that blocks
the commit.

`polix install` always registers the hooks in the git configuration of the repository, like the hooks of Claude Code,
even when polix.yaml has no `githooks`; `polix uninstall` removes them and `polix doctor` warns when git does not run
them.
It relies on the hooks git reads from its configuration, which only recent git versions have: an older git ignores
them, and install and doctor say so.
The events of the AI, `on.pre_commit` included, do not change.

`polix install --githooks` installs only the hooks of git, without asking and printing only what changed.
A polix.yaml that declares githooks runs it by itself at the start of every session of the AI, with nothing more to
write, so each person who works on the repository with the AI has the hooks; removing the githooks turns it off.
When git is too old to run them, it says so and fails, so the AI learns at the start that the git gates do not apply.
This repository declares a githook of its own: a commit that stages polix.yaml or the rules runs `polix config check`.
The confirmation of install and uninstall now names the hooks of git as well.

## Context

`polix hook <claude|codex>` (`internal/app/hook/answer`) evaluates `on.pre_commit` only when it recognises a
`git commit` in a command of the AI, by a heuristic (`logic_commit.go`, `logic_cmdline.go`), so the commits of people
and the commits of the AI the heuristic misses are never gated.
polix.yaml has no place for gates that git applies to every commit, and polix registers no git hook.
git 2.54 and later run hooks declared in their configuration (`hook.<name>.event` and `hook.<name>.command`), listed
by `git hook list <event>`, so no wrapper script is needed.

## Constraints

- The events of the AI, `on` and `guardrails`, keep their behaviour: `on.pre_commit` and `protected_branches` are not
  evaluated by git (the request: the AI events do not process git, and git only processes githooks).
- The new code is a vertical slice of its own, `internal/app/githook/answer`, with its domain `internal/app/githook`
  (the request); it imports no other use case (GOARCH-9).
- It runs on Linux, macOS and Windows (XPLAT-1); git runs a configured hook command through its shell, also on
  Windows with Git for Windows.
- A change of the format of polix.yaml updates `docs/polix.md` and `examples/polix.yaml` (DOC-1).
- The hooks git reads from its configuration need git 2.54 or later; an older git ignores the keys without error.
- Code, comments and docs are in English (GO-2).
- `polix install` without `--githooks` keeps its behaviour, its exit 0 with a git that does not list the hooks (AC12)
  included; only its confirmation summary gains the hooks of git.
- A `run` of `start` runs without a shell from the root, never blocks, and reaches the AI only when it fails; it is
  not run again once it passed on the same content and HEAD unless it has `always: true` (`docs/polix.md`, Verbs and
  How often each verb acts).
- `examples/polix.yaml` and `plugins/polix/skills/workflow/reference.yaml` stay byte copies (test of `plugins`), and
  every recipe of `docs/use-cases.md` stays valid (`TestUseCasesAreValid`).
- The shortcuts of `guardrails` expand into entries of `on` before the entries written in each event, each with the
  path of its shortcut in `workflow.Entry.From` and the line of its item, which `polix graph` and the log name
  (`workflow.Guardrails.Expand`, `internal/app/workflow/workflow_shortcuts.go`); `polix config fmt` writes only what
  the file holds.
- A polix.yaml without `githooks`, or whose githooks events are all empty, loads into the same entries as before.

## Decisions

- `githooks` is a top level section of polix.yaml, apart from `on`; its events are `pre_commit` and `commit_msg`
  (interview: separate section; only those two events, the other git events are not needed).
- A githooks entry keeps the shape of an entry of `on`: `when`, `unless` and `action` (interview: own vocabulary).
- Verbs: `block` and `run` only; `inject` and `notify` are problems (interview).
- `block` takes its message, short or long form; `once` is a problem, since githooks use no log (interview: no log).
- `run` takes a command (a string split on spaces, or a list) and `message`; `rules` and `always` are problems
  (interview: command and message).
- Conditions: `branch`, `changed` and, only in `commit_msg`, `message`; any other condition, `any` and `not`
  included, is a problem (interview).
- `changed` and `message` take a string or a list, and hold when one item matches; negation is written with `unless`
  (interview: lists, without any nor not).
- `changed` matches the files staged for the commit, the index against HEAD, with the globs of `on` (interview).
- `message` is a regular expression, or a list of them, matched against the first line of the message, after removing
  the comment lines and what follows the scissors line (interview: option B, only the first line; comment lines of
  core.commentChar).
- Placeholders: `{branch}` everywhere, `{message}` only in `commit_msg`, and the variables of `vars`, in the texts of
  the verbs and in the patterns of `changed` and `message`; any other placeholder is a problem (interview).
- githooks use no log of polix: every `run` runs on every commit, nothing is written to `<git-dir>/polix` (interview).
- A `run` has no time limit, its output goes live to the terminal of the commit, and on failure polix prints its
  `message` and the line `<command> failed: <error>` and blocks (interview).
- A polix.yaml that cannot be used (broken YAML, problems, a newer `requires`) blocks every commit with its problems
  (interview).
- The merges and other messages git generates get no special treatment: an entry lets them through with `unless`
  (interview).
- The command is `polix githook <pre-commit|commit-msg> [file]`, hidden from the help like `polix hook` (interview).
- The evaluation of `branch`, `changed`, the placeholders and `vars` is implemented again in the new slice, not
  moved out of `hook/answer` (interview: own implementation).
- `polix install` always writes the hooks into the local git configuration of the repository, also without
  `githooks`, and never with `--user` nor outside a repository (interview).
- The hook command is plain `polix`, not an absolute path (interview).
- Only the local git configuration, never `~/.gitconfig` (interview).
- When git does not list the hooks after install, install keeps them and warns (interview: write and warn).
- `polix doctor` always warns, never fails, when git does not list the hooks of polix (interview).
- `polix config fmt` formats `githooks` and `polix doctor` checks the hooks; `polix graph` does not show githooks
  (interview).
- The end to end tests skip, naming the git version, when git does not run hooks from its configuration (interview).
- The names of the git configuration are `hook.polix-pre-commit` and `hook.polix-commit-msg`: git forbids a name equal
  to an event (git-config(1)).
- Without polix.yaml, without entries for the event, or outside a repository, `polix githook` exits 0 silently; an
  unknown event argument exits 1 with the error, as `polix hook` does for an unknown agent (code of `hook/answer`).
- When `core.commentChar` is unset or `auto`, the comment character is `#`; `core.commentString` wins over
  `core.commentChar` when both are set (git-config(1)).
- `polix install --githooks` writes only the two hooks of git of the repository: no plugin, no hooks of the agents, no
  marketplace (the request: install only the githooks).
- `--githooks` never asks for confirmation and prints only the lines of what changed, nothing when the hooks are
  already there; `--yes` and `--quiet` are accepted and change nothing (interview: no confirmation, only changes).
- When git does not list the hooks after `--githooks`, it keeps them, prints the warning of AC12 on stderr and exits
  1, so a `run` of `start` reaches the AI (interview: exit 1 with the warning).
- `--githooks` with `--user` or with `--agent` is an error of the flags, and `--githooks` outside a repository is an
  error; each exits 1 and writes nothing (interview: an error in every case).
- A polix.yaml whose `githooks` has at least one entry expands, implicitly, into an entry of `start` that runs
  `polix install --githooks` with `always: true`, so it runs on every session start and puts back hooks removed by
  hand; there is no key to turn it off, and removing the githooks entries does (interview: option 1, implicit,
  without an option to disable it).
- The expanded entry has the fixed message
  "The hooks of git of githooks are not installed, so the gates of githooks do not apply to the commits:", which
  reaches the AI before the failure line when the run fails (interview: a fixed message).
- The expanded entry goes before the entries written in `start`, with `From` `githooks` and the line of the first
  githooks event with entries, as the shortcuts of `guardrails` do (`Constraints`); `polix graph` draws it as
  `from githooks`, while the githooks entries themselves stay out of the graph (interview: shown as a shortcut).
- No recipe is written by hand: the docs, `docs/use-cases.md` and `examples/polix.yaml` explain that declaring
  githooks is enough.
- The `polix.yaml` of this repository gains a githooks `pre_commit` entry that runs `polix config check` when
  `polix.yaml` or `ai/rules/**` is staged, which also validates the rules (interview: config and rules check).
- The confirmation summary of `polix install` and `polix uninstall` names the hooks of git it writes or removes in
  the local git configuration (interview: the minor finding of review rev03, in the same task).
- No `polix uninstall --githooks`: `polix uninstall` keeps removing them as it does (interview).

## Approach

Format of polix.yaml.
`workflow.Workflow` gains `Githooks`, the entries of each githooks event as `workflow.Entry`, and `GithookLines`, the
line of each event.
The vocabulary of `internal/app/workflow/workflow_vocabulary.go` gains the githooks events, `pre_commit` and
`commit_msg`, as a list of their own, apart from `workflow.Events`, and the condition `message`.
`TopKeys` gains `githooks`.
The validator of the domain gets a githooks pass: an unknown githooks event, a verb other than `block` or `run`,
`once`, `rules` or `always`, a condition other than `branch`, `changed` and `message` (and `message` outside
`commit_msg`), an empty pattern, a regular expression that does not compile, and an unknown placeholder, each reported
on the line of its entry, as the problems of `on` are.
The load use case decodes `githooks` with the decoding types of the entries of `on`.
The format use case orders `githooks` after `on`, with its events in the order `pre_commit`, `commit_msg`, and its
entries spaced and ordered as those of `on`.

Domain `internal/app/githook`.
The entity `Githook` (`githook.go`) is one call of git: the githooks event, the branch, the staged files and, on
`commit_msg`, the first line of the message, with `Valid`.
It holds the result of the runs already carried out, in order, so the logic can take the step shape: an entry after a
`run` must know whether it passed.

Use case `internal/app/githook/answer` (`AnswerGithook`).
`in.go`: `Command` is `polix githook <pre-commit|commit-msg> [file]`, hidden, with `--dir`; it maps the git event name
to the githooks event and validates it; `Request` has the event, the message file, the folder and the running version;
`Response` has the text for stderr and the exit code.
The shell opens the repository, loads polix.yaml through the loader of `workflow/load`, reads the branch, the staged
files and, on `commit_msg`, the message and the comment character, then loops on `Decide` and carries out each run.
`logic.go`: `Decide` walks the entries of the event in order, evaluates `when` and `unless` with branch, changed and
message, expands the placeholders, and returns the next run, or the answer: pass, or block with the reasons.
The first entry that blocks ends the evaluation, as in `on`.
A workflow that cannot be used answers block with its problems, and `polix update` when it requires a newer polix.
`out.go`: `Adapter` with the loader of the workflow; git through `internal/platform/git` (branch, staged files, the
comment character, the message file) and the run through `internal/platform/proc`, with the output live.
Exit codes: 0 lets the commit go on, 1 aborts it; reasons on stderr, each prefixed `polix: `.

Install, uninstall and doctor.
`internal/platform/git` gains the writing, removal and listing of hooks in the local configuration.
`setup/install` writes `hook.polix-pre-commit` (event `pre-commit`, command `polix githook pre-commit`) and
`hook.polix-commit-msg` (event `commit-msg`, command `polix githook commit-msg`), replacing the values it had, and
reports the change; then it lists the hooks of git and warns when they are not listed.
`setup/uninstall` removes both sections and reports the change.
`setup/diagnose` lists the hooks of both events and warns when one of polix is missing or git cannot list hooks.

Install of the hooks of git alone.
`setup/install` `Request` gains `GitHooks`, set by the flag `--githooks`; the command rejects it with `--user` or
`--agent` before running anything.
The logic decides a githooks-only output: the two hooks of `setup.GitHooks`, no plugin, no hooks of the agents and
no confirmation, or a failure when the setup has no root, that is outside a repository.
The shell, on that output, writes each hook through `RegisterGitHook`, asks `Unlisted`, and returns the changes; the
response marks the githooks-only mode, so the command prints only the changes and, when some hook is unlisted, the
warning on stderr and the exit code 1.
`setup.Setup.Summary` takes the hooks of git to name, and install and uninstall pass their `Output.GitHooks`, so the
summary adds a line for the hooks of git in the local git configuration when there are some.

Implicit install from githooks.
The domain `internal/app/workflow` gains, in `workflow_githooks.go`, the expansion of githooks into `on`: given the
entries of `on` and the githooks of the workflow, it returns `on` with one more entry first in `start` when some
githooks event has entries, built as the run entries of the shortcuts are (`Cond.shortcutRun` of
`workflow_shortcuts.go`, with `always`), with the command `polix install --githooks`, the fixed message, `From`
`githooks` and the line of the first githooks event with entries; otherwise `on` unchanged.
The load use case calls it after `Guardrails.Expand` in `internal/app/workflow/load/out_workflow.go`, so every
reader of the workflow (`polix hook`, `polix graph`, `polix config check`) sees the entry, and `polix config fmt`,
which formats the file as written, never writes it.

### Discarded alternatives

- Evaluating `on.pre_commit` from git with an actor inherited from the AI: the request keeps git and AI apart.
- A third format `git` in `polix hook`: the request asks for its own vertical slice.
- `polix hook git <event>`: the command of `hook/answer` would dispatch to two use cases (GOARCH-15).
- Moving the evaluation of conditions to the workflow domain: the user chose an own implementation.
- An absolute path to the binary in the git configuration: it depends on the machine (the user).
- `pre_push` and the other git events: not needed (the user).
- Registering the hooks of git from the session start hook of polix itself: the session start hook never installs
  anything nor touches the files of the repository (`docs/polix.md`), and the request asks for an option of install.
- `polix uninstall --githooks`: not asked (the user).
- A start entry written by hand in each polix.yaml: easy to get wrong without `always: true` (the user chose implicit).
- A key `install` inside `githooks`: it mixes an option with the events of the map (the user chose implicit).
- A shortcut of `guardrails` such as `githooks_on_start`: far from the githooks section (the user chose implicit).
- A key to turn the implicit entry off: removing the githooks entries does it (the user).
- Fixers that re-stage files, as the pre-commit of platform does: out of the request, which only runs and blocks.

## Acceptance criteria

- AC1: A polix.yaml with `githooks: { pre_commit: [...], commit_msg: [...] }` loads, and `polix config check` reports
  no problem for entries that use `branch`, `changed`, `message` (in `commit_msg`), `block`, `run` with `command` and
  `message`, `{branch}`, `{message}` (in `commit_msg`) and a variable of `vars`.
- AC2: `polix config check` reports, each on the line of its entry: an unknown githooks event (`pre_push`), the verbs
  `inject` and `notify`, `block` with `once`, `run` with `rules` or `always`, a condition other than `branch`,
  `changed` and `message` (`actor`, `any`, `not` included), `message` in `pre_commit`, `{message}` in `pre_commit`,
  another placeholder (`{path}`), an empty pattern and a regular expression of `branch` or `message` that does not
  compile.
- AC3: `polix config fmt` writes `githooks` after `on`, `pre_commit` before `commit_msg`, and the entries and keys of
  githooks as those of `on`; a file already formatted stays the same.
- AC4: `polix githook pre-commit` on a repository whose githooks `pre_commit` entry has `when: { branch: "^main$" }`
  and `action: { block: "No se commitea en main" }` exits 1 on `main` with `polix: No se commitea en main` on stderr,
  and exits 0 on another branch.
- AC5: `changed` in githooks holds only for files staged for the commit: a file modified and not staged does not make
  it hold, a staged file matching the glob does, and a list holds when one glob matches.
- AC6: A githooks `run` runs its command from the root of the repository on every commit, its output reaches the
  terminal while it runs, and when it fails `polix githook` prints its `message` and `<command> failed: <error>` on
  stderr and exits 1; when it passes, the next entries are evaluated.
- AC7: `polix githook commit-msg <file>` matches `message` against the first line of the message, after removing the
  lines that start with the comment character of git (`#` by default, or `core.commentChar` / `core.commentString`)
  and everything from the scissors line on; a list holds when one pattern matches.
- AC8: The placeholders `{branch}`, `{message}` (on `commit_msg`) and the variables of `vars` expand in the messages
  of `block` and `run`, the command of `run`, and the patterns of `changed` and `message`; with
  `vars: { key: { branch: "^([A-Z][A-Z0-9]+-[0-9]+)" } }`, `when: { branch: "^[A-Z]+-[0-9]+" }`,
  `unless: { message: "^{key}: " }` blocks the message `arregla el login` on branch `PROJ-12-login` and lets
  `PROJ-12: arregla el login` through.
- AC9: Without polix.yaml, without entries for the event, or outside a repository, `polix githook` exits 0 and prints
  nothing; with a polix.yaml that cannot be used it exits 1 and prints its problems; an unknown event exits 1.
- AC10: `polix githook` writes nothing to the log of polix (`<git-dir>/polix`).
- AC11: `polix install` (without `--user`, inside a repository) writes `hook.polix-pre-commit.event=pre-commit`,
  `hook.polix-pre-commit.command=polix githook pre-commit`, `hook.polix-commit-msg.event=commit-msg` and
  `hook.polix-commit-msg.command=polix githook commit-msg` into the local git configuration, also without
  `githooks` in polix.yaml, reports the change, and running it twice leaves one event per hook.
- AC12: When git does not list those hooks after install, `polix install` keeps them and warns that git does not run
  hooks from its configuration, so githooks do not apply until git is updated.
- AC13: `polix install --user` and `polix install` outside a repository do not touch any git configuration.
- AC14: `polix uninstall` removes `hook.polix-pre-commit` and `hook.polix-commit-msg` from the local git configuration
  and reports it; other hooks of the configuration stay.
- AC15: `polix doctor` gives an ok line when git lists the hooks of polix for `pre-commit` and `commit-msg`, and a
  warning, never a failure, when one is missing (asking to run `polix install`) or git cannot list hooks.
- AC16: With the hooks installed, a real `git commit` on a repository whose githooks block it fails with the reason,
  and one that passes is created; the test skips, naming the git version, when git does not run hooks from its
  configuration.
- AC17: The events of the AI do not change: `polix hook claude` evaluates `on.pre_commit` as before and never the
  entries of `githooks`.
- AC18: `polix install --githooks` inside a repository writes the four keys of AC11 and nothing else (no plugin, no
  `.claude/settings.json`, no marketplace), never asks for confirmation, prints only the lines of what changed, and
  exits 0; a second run prints nothing and exits 0.
- AC19: When git does not list the hooks after `polix install --githooks`, the keys stay, the warning of AC12 is on
  stderr and the exit code is 1; `polix install` without `--githooks` still exits 0 in that case.
- AC20: `polix install --githooks --user`, `polix install --githooks --agent claude` and `polix install --githooks`
  outside a repository each exit 1 with an error and touch no git configuration nor file.
- AC21: The confirmation summary of `polix install` names the hooks of git it writes in the local git configuration,
  and that of `polix uninstall` the ones it removes, when there are some; without a repository it names none.
- AC22: A polix.yaml with at least one githooks entry loads with one more entry first in `start`, from `githooks`,
  that runs `polix install --githooks` with `always: true` and the message
  "The hooks of git of githooks are not installed, so the gates of githooks do not apply to the commits:"; a
  polix.yaml without `githooks`, or with only empty githooks events, loads without it; `polix config fmt` never
  writes it and `polix graph` draws it as `from githooks`.
- AC23: With a githooks entry and no start entry written for it, a session start of the AI (`polix hook claude` on
  `SessionStart`) in a repository without the hooks of git leaves `hook.polix-pre-commit` and
  `hook.polix-commit-msg` in its local git configuration.
- AC24: The `polix.yaml` of this repository has a githooks `pre_commit` entry that runs `polix config check` when
  `polix.yaml` or `ai/rules/**` is staged, and `polix config check` passes on it.

## Out of scope

- `pre_push` and every other git event: the user does not need them.
- Fixers that change and re-stage files: the request only runs and blocks.
- The global git configuration (`~/.gitconfig`): the user chose local only.
- A condition on who makes the commit: githooks are the same for everyone.
- `polix graph` showing githooks: not chosen; only the implicit start entry appears, as `from githooks`.
- Moving the evaluation of conditions of `hook/answer` to the domain: the user chose an own implementation.
- `polix uninstall --githooks`: not asked.
- A person who never opens a session of the AI in the repository: the `start` entry does not reach them, and they get
  the hooks of git with `polix install`.

## Risks

- git older than 2.54 ignores the hooks without error, so a team may believe it is gated: install and doctor warn.
- A GUI client without `polix` on its PATH aborts every commit with command not found: document it; the user chose
  plain `polix`.
- A slow `run` slows every commit, with no time limit: document that a `run` of githooks runs on every commit.
- `core.commentChar auto` makes git pick a character polix cannot know: polix uses `#`, documented.
- A broken polix.yaml blocks every commit of everyone: the message names the problems and `--no-verify` bypasses it.
- The AI can bypass with `--no-verify`: document a `forbidden_commands` pattern for it in the docs of githooks.
- The evaluation of `branch`, `changed` and placeholders exists twice and may diverge from `on`: the tests of
  githooks pin their behaviour with the same examples as the docs of `on`.
- The implicit `start` entry runs the `polix` on the PATH: a binary older than Task 7 rejects `--githooks`, and in
  this repository the failed run reaches the AI on every session start until `just install`.
- A repository that declares githooks for people only still gets the implicit entry in the sessions of the AI: the
  user chose no switch; removing the githooks turns it off.
- `polix install --githooks` runs on every session start: it is two writes of git configuration, and a failure never
  blocks the session, since a `run` of `start` only informs.
- With a git older than 2.54, every session start tells the AI that the git gates do not apply, by design (exit 1).
